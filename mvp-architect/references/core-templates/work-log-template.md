# WORK_LOG.md Template

Generate `docs/WORK_LOG.md` during Phase C as a living factual close log. It grows one `## <work item>` section per item, written at close with result, evidence, consequence and links.

Where present, the Work tracker is the one-line index; otherwise `docs/plans/` is the index. `WORK_LOG.md` stays short by linking to canonical detail.

Two things `WORK_LOG.md` is **not**:

- **Not loaded every session.** Read it on demand; it is not part of the standard pre-phase order.
- **Not the canonical source of detail.** Record fact, evidence and consequence, then link to canonical artifacts.

## `docs/WORK_LOG.md`

````markdown
# Work log

> Factual per-work-item close for [Product Name]. Its index is the Work tracker where present, otherwise `docs/plans/`.
>
> **Not loaded every session.** Unlike the fact sheet, this is history; read it on demand for the full story of a past work item.
>
> **Not the canonical source of detail.** Each section records fact, evidence and consequence and links to canonical detail.
>
> **Source:** scaffold generated by mvp-architect on YYYY-MM-DD. One `## <work item>` section is added per work item, at close (sdi-mode Step 8 housekeeping). Sections stay in the same order as the Work tracker rows where there is a tracker, and chronological where there is none; either way the newest is appended at the end.

---

## Project planning (mvp-architect Phase C)

**Type:** maintenance · **Status:** ✓ · **Date:** YYYY-MM-DD
**Plan:** n/a (initial bundle)

Ran mvp-architect Phase 0–C for [Product Name]. ## Per-section format (one section per work item, added at close)

When a work item's end-of-phase housekeeping (sdi-mode Step 8) closes the item, add a section like this; where the fact sheet has a Work tracker, reduce that item's row to a single line at the same time:

```markdown
## <work item slug or Phase N>

**Type:** feature | bugfix | maintenance | migration | refactor | perf | phase · **Status:** ✓ | ✓ Merged→main | ⏸ | ... · **Date:** YYYY-MM-DD
**Plan:** docs/IMPLEMENTATION_PLAN_<name>.md · **PR:** [#NN](url) *(if any)*

[Result: what changed. Evidence: links to relevant checks/commits/reviews. Consequence: current status or next action. Cross-link DECISIONS, KI, plan and PR; do not narrate rounds or inventory suite totals.]
```

Rules:

- **Match the tracker, where present.** The section's `Type` / `Status` / `Date` and slug match the index row. Without a tracker, `docs/plans/` is the index.
- **Order.** With a tracker, keep sections in the same order as its rows; without one, keep them chronological. Either way, append the newest at the end.
- **Cross-reference, don't duplicate.** "DECISIONS #28–#31 written", "KI-049 Resolved (commit, date)", "PR #7 → test" — link/point, don't paste the entries' content.
- **Write at close, not continuously.** The section is a factual linked close, updated only if the item reopens.

## Length discipline

~20–40 lines at birth (header + Phase C section). It grows one section per work item; a section is typically 5–30 lines depending on the item's size. There is no hard cap — this file is allowed to be long because it is the archive — but each section should consolidate, not transcribe. If a section is reproducing the full content of DECISIONS / KNOWN_ISSUES / a round report, cut it down to pointers.

## What goes here vs the other surfaces

| Surface | Holds | Loaded each session? |
|---|---|---|
| **Work tracker** (`AGENTS.md` / `CLAUDE.md`), where the project has one | one-line index per item: status + pointers | yes (part of the fact sheet) |
| **`WORK_LOG.md`** | factual result/evidence/consequence links at close | no — read on demand |
| `DECISIONS.md` | atemporal "why we chose X" | skimmed at audit |
| `KNOWN_ISSUES.md` | append-only "what we know is wrong" | skimmed at audit |
| `docs/memory/YYYY-MM-DD.md` | datable "what happened today / what's next" | recent entries, yes |

`WORK_LOG.md` is per-item and written at close; `docs/memory/` is per-day. A daily entry points to the close rather than duplicating it.
